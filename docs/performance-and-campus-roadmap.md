# 生成性能分析与校招增量开发路线

> 本文保留第一轮审查时的现状。后续已实现自适应快速成文、正文优先发布、字幕单轨下载、HTTP 复用和并行截图；当前实现与新基准请看 [生成架构说明](generation-architecture.md)。

代码审查与离线验证日期：2026-10-15。

## 1. 当前项目具备什么

React + TypeScript 前端、FastAPI 后端、SQLAlchemy + SQLite 存储；支持视频字幕提取、长字幕分段摘要、大纲与章节生成、FFmpeg 关键帧、视觉图注、HTML/Markdown 导出、问答卡片、历史记录、IMA 导出和 Docker Compose 部署。

核心业务已经完整，适合作为校招项目继续深化。当前最有价值的方向是把长耗时生成变成可测量、可恢复、可追溯的任务系统，并展示优化前后的证据。

现有 `enterprise_ai_portfolio_advice.md` 包含较广的技术建议，其中“引入多模态视觉”已经有代码实现，不应继续作为未开发功能。此文按当前实现重新排序。

## 2. 慢在哪里

主链路位于 `backend/services/generator.py`：

```text
视频信息和字幕
  → 关键帧规划 → FFmpeg 截图 → 视觉图注（符合条件时）
  → 短文生成
    或 [分段摘要 → 大纲 → 分章生成]
  → 模板/Markdown → 问答卡片 → 保存文章 → 标记完成
```

| 代码证据 | 直接影响 | 本轮处理 |
| --- | --- | --- |
| 每 3000 字一段，原来逐段 await 摘要 | 长字幕等待时间随段数叠加 | 改为受控并发，保持摘要顺序 |
| 大纲要求 5–8 章，原来逐章 await，每章要求约 800–1200 字 | 输出规模大，章节延迟叠加 | 章节受控并发，保持章节顺序 |
| 图注原来逐帧 await | 多张图片连续等待远端模型 | 图注受控并发 |
| async 后台函数直接调用同步 yt-dlp 和 subprocess | 阻塞事件循环，其他任务和进度查询也可能卡顿 | 将解析与截图移至工作线程 |
| 模板完成后仍等待卡片请求才保存 | 用户不能先看已经生成的正文 | 作为下一阶段的正文优先交付功能 |
| 缺少阶段耗时 | 无法区分下载慢、模型慢、截图慢 | 日志加入阶段耗时和总耗时 |

例如 30000 字字幕需要 10 次摘要请求，加上 1 次大纲、5–8 次章节、1 次卡片，总计 17–20 次文本请求；如果进入关键帧流程，还会多 1 次规划和若干视觉请求。并发优化减少串行等待，不减少这些请求的 Token 与费用。

FFmpeg 每次截图调用的超时为 20 秒，黑帧还可能触发偏移重试。当前仍逐个时间点截图，因此截图阶段可能继续成为瓶颈。应先读新增日志，再决定是否引入小规模截图并行及阶段超时预算。

字幕提取配置会请求多种语言；后续可以改成先发现轨道、按偏好只下载一份字幕，并以视频 ID 隔离临时目录。当前共享临时文件命名还可能导致同一视频的并发提取互相干扰。

这些是代码确认的等待路径；尚未调用用户的真实模型，不能据此断言线上各阶段占比。

## 3. 本轮实现及边界

- 新增 `services/pipeline.py`：有界并发、按输入顺序返回结果、某个子任务失败后取消并等待其余协程结束。
- 摘要、章节和图注默认单任务并发上限为 3；`GENERATION_CONCURRENCY` 可设为 1–8。适配严格限流时设为 1。并发配置在每批执行时读取。
- yt-dlp 工作线程只把日志字符串写入队列；数据库写入仍发生在事件循环线程，避免共享 Session 跨线程操作。
- FFmpeg 截图整体移至工作线程，单个任务内部仍按原顺序截图。
- 并发阶段按完成数量更新进度，修复视觉阶段结束后进度退回 30% 的问题。
- 修复短字幕分支未初始化 `chapters_outline` 导致归档失败的问题；短文目录从正文 h2 中提取。
- 增加解析、视觉、摘要、大纲、正文、排版与卡片、总耗时日志。

并发上限目前按单个生成任务计算，多个用户同时提交时会相乘。同步数据库操作仍在事件循环中；这次只移除了更重的下载与截图阻塞。线程中的下载/截图开始后，协程取消不能强制终止该线程；真正的取消任务需要管理下载器和子进程生命周期。协程取消也不能保证供应商已经接收的请求停止计费。

日志中的 Tokens 仍沿用原有文本生成统计口径，没有包含关键帧 Planner 和视觉调用，不应作为完整账单。阶段耗时包括边界间的本地处理开销，其中模板与卡片合并计时。

## 4. 验证结果与复现

后端测试：`python -m unittest discover -s tests -v`，15 项全部通过。覆盖长短文章保存、并发上限、乱序响应后的章节排序、Token 汇总、线程隔离、视觉并发、进度单调、失败取消、下载失败日志和已有截图/视觉功能。测试输出仍有依赖弃用及数据库资源警告。

从 backend 目录运行离线基准：

```powershell
.\.venv\Scripts\python.exe tests/benchmark_generation.py
```

基准用内存 SQLite 和模拟模型调用，输入为 15000 字字幕、5 段摘要、5 个章节，先预热，再分别运行 5 次取中位数：

| 配置 | 本次中位耗时 |
| --- | --- |
| 并发 1 | 0.361 秒 |
| 并发 3 | 0.207 秒 |

该受控样例约为 1.75 倍速度，耗时减少 42.8%。它验证的是本地调度效果，不含真实视频下载、模型响应、限流或视觉耗时。并发 1 是新实现的串行配置，不是旧版本的线上基线；此数字不能写成“真实视频生成提速 42.8%”。

真实测量建议：固定供应商、模型、Prompt、字幕和输出要求；短/中/长各选视频，分别测并发 1 与 3，并记录字幕提取、截图、摘要、写作、卡片耗时。至少积累 30 次每种配置的运行，再报告样本数量、P50/P95、成功率、429 比例和 Token。单列首次可读正文时间与全部附件完成时间。人工抽查事实准确度、重复内容和章节衔接，避免用文章变短换取速度。

## 5. 作为校招项目，优先增量开发什么

建议定位：**面向长视频的多模态知识整理系统，支持可恢复的生成流水线与时间戳证据回溯**。下面是工程判断与实施建议，不是招聘市场统计。

| 优先级 | 功能及具体实现 | 面试能讲什么 | 可演示的验收标准 |
| --- | --- | --- | --- |
| P0 | 持久化分阶段结果：字幕、摘要、章节分别保存；失败只重跑失败阶段；任务幂等 | 状态机、事务边界、重复消费、恢复策略 | 第 4 章故意失败，重试复用已完成内容；重启后任务可恢复；同一任务不重复归档 |
| P0 | 任务队列与服务级限流：API 接收与 Worker 分离；按供应商限制总并发；区分 429/超时/参数错误 | 背压、调度、公平性、退避、重试边界 | 同时提交多个任务，API 保持可响应；总并发受限；401 不重试、429 有预算地退避 |
| P0 | SSE 进度与正文优先交付：正文先保存，卡片等附件独立状态，支持重连与历史事件补发 | 流式协议、状态同步、断线恢复、一致性 | 正文可读时即可打开；卡片失败不丢正文；刷新恢复进度；断线重连不重复章节 |
| P1 | 证据可追溯：保留字幕 start/end 与 segment_id，章节绑定证据片段，截图对应真实时间 | 数据建模、生成可信度、检索与生成边界 | 点击段落跳回视频时间；没有证据的结论有明确标记；能看到原字幕和截图 |
| P1 | 生成评测与可观测性：每次调用记录模型、耗时、用量、错误、Prompt 版本；建立固定评测集 | 性能分析、成本控制、实验可重复性 | 给出固定样本上的时延/成功率/成本对照及人工事实抽查结果 |
| P2 | 缓存与局部重生成：字幕缓存、模型/Prompt/参数组成缓存键，支持只改写选中章节 | 缓存失效、依赖追踪、版本管理 | 同视频换主题只重新渲染；换 Prompt 只失效相关生成结果；不同权限内容不会串缓存 |
| P2 | 多用户权限与资源隔离，前提是要部署成公共服务 | 鉴权、越权防护、配额与数据隔离 | 用户 A 无法读取 B 的文章、任务和截图；超配额有明确响应 |

后端岗优先做持久化恢复、队列限流、幂等和故障注入；AI 应用岗优先做时间戳证据、评测集和可解释的模型路由；前端岗可深入 SSE 重连、分章节增量展示、编辑版本和长文性能。默认建议走后端 + AI 应用路线。

SSE 本身减少进度轮询和首次展示等待，不能自动缩短模型生成时间。模型 Token 流、完整章节事件和任务进度事件是不同层次，第一版可以先推送完整章节，再做 Token 级增量。

## 6. 先修好现有基础能力

审查发现的未处理问题，适合在扩展前安排一轮质量修复：

1. **供应商配置未贯通**：SettingsPanel 保存 MiniMax/GLM 密钥，但 `getApiHeaders()` 与 `create_task()` 未传递/接收相应头；SiliconFlow 也没有完整密钥通路。TaskCreate 默认 Gemini，而文本调用器不支持 Gemini。需要统一供应商注册表和契约测试。
2. **关键帧缺少时间证据**：字幕清洗删掉时间戳，Planner 只看到前 15000 字纯文本，却输出秒数。模型给出的时间只能视为猜测；应保留带时间片段，再做定位和局部截图。
3. **视觉配置混用**：自定义文本服务也被用于固定 `gpt-4o-mini` 视觉请求；如果端点已经包含 `/chat/completions`，视觉路径还会重复拼接。需要独立配置视觉端点/模型，并在不支持视觉时明确降级。
4. **无凭据时的图注仍像事实**：视觉服务失败后返回“核心架构与关键流程演示”一类通用文本，应改成注明未识别，避免把猜测当作画面结论。
5. **前端轮询合并存在竞态**：`addedSincePoll` 通过当前 prevIds 排除 prev 自身，条件始终不成立。轮询进行时新提交的任务可能被覆盖，需按轮询开始时的 ID 集合合并。
6. **部署数据不完整**：Compose 只持久化数据库，没有持久化 snapshots；重建容器可能保留文章而丢图。导出 HTML 的相对图片路径也需要打包或改成可离线使用的资源。
7. **文档和接口能力不一致**：README 的 React 版本与 package.json 不一致，语言实现目前也只区分 zh 与其余值。文档应描述已验证能力。

## 7. 建议的实施顺序与交付物

按四个里程碑推进，周期由投入时间和熟悉程度决定：

1. 完成基础配置修复，拿真实视频建立性能/质量基线，补 CI 和依赖锁定。
2. 阶段结果持久化、任务队列、服务级限流、失败重试与恢复；补故障注入测试。
3. 正文优先交付、SSE、断线恢复；保留字幕时间戳并支持来源回跳。
4. 固定评测集、运行看板、架构说明、部署演示和简历材料。

每个阶段留下可以展示的证据：架构图、状态流转图、接口示例、一次故障恢复录像、基准原始数据、质量抽查表和可复现命令。先把这些做好，再按真实需求增加 RAG、搜索或更复杂的工作流框架。

简历示例（数字需要自己测量后填写）：

> 基于 FastAPI/React 构建长视频多模态知识整理系统，设计有界并发生成流水线、阶段持久化与失败恢复；通过供应商限流和章节顺序汇总，在固定评测集上将 P50 生成耗时从 A 降至 B，并记录事实一致性与 Token 成本。
